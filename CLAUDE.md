## What this is

> **The user's own website asks live in `REQUESTS.md`** (R-001…, quoted in their words, each with a "Done means" checklist). They outrank persona feedback, and every `/evolve` cycle advances the top open one. **Planning lives in `PLAN.md`** — principles every change is judged against, the self-evolving persona loop, the ranked backlog, and the evolution log. `IDEAS.md` is raw idea material.

Beobeo — a multi-user financial companion / portfolio tracker (stocks, ETFs, funds, crypto). Differentiators: best-in-class position detail (lots, cost basis, per-year realized gains) with finance-grade visualizations, and a DCA counterfactual ("would the same dollars in SPY have done better?"). A mobile app (Expo/React Native) is planned later — which is why all domain logic is framework-free — and it's intended to eventually serve public users.

### `packages/core` — domain engine (the correctness-critical part)
Pure TS, zero framework/DB deps. Exhaustive Vitest fixtures in `packages/core/test/` — **any engine change must extend these tests; hand-compute expected values.**
- `buildLots(txns)` — FIFO lot engine. Input must be pre-sorted by `tradedAt` (throws `UNSORTED_INPUT`). Sells match FIFO with proportional fee allocation; oversells throw `EngineError("OVERSELL")` (never clamp). Splits multiply lot quantity, basis unchanged, acquisition date preserved (holding period survives splits). `transfer_in` without price = zero basis (conservative). `transfer_out` removes units FIFO without realizing.
- Conventions: split ratio lives in `quantity` (4 = 4-for-1, 0.25 = reverse); dividend cash = `quantity × pricePerUnit` (importers set qty=1, price=total); standalone `fee` txns touch no lots.
- `isLongTerm` — strictly greater than one year (US rule; exactly 1 year = short).
- `positionFromLots`, `realizedByYear` (calendar year of sale, UTC; short/long split).
- `portfolioTimeSeries` — daily value from holdings × forward-filled closes + cumulative invested line. Assets with no price yet contribute 0.
- `replayDca(flows, benchmarkBasket, to)` — buys benchmark at flow date's close (next trading day if closed — `onOrAfter` lookup); withdrawals sell proportionally, clamped at 0 units; weighted baskets supported. Returns series + XIRR. **Benchmark series must be split-adjusted first** (see `adjustForSplits`) — synthetic positions have no split transactions, so unadjusted closes cliff by the ratio on split dates.
- `adjustForSplits(prices, splits)` / `splitFactorAfter(splits, date)` (`splits.ts`) — divide closes strictly before each split date by the compounded ratio, expressing a series in present-day units. Used for DCA benchmarks and position-chart display.
- `xirr` — Newton + bisection fallback; floats are fine here (it's a rate), Decimals everywhere else.
- `buysVsBenchmark(txns, latestPrices, benchmark)` (`buys-vs-benchmark.ts`, 3 tests) — each buy (cost = qty × price + fees) valued now as if still held (units scaled by the user's split txns strictly after the buy date) next to the same dollars put into the benchmark that day (`onOrAfter` close, so a weekend buy fills at the next close), edge = value − benchmark value, worst first, unpriced rows last. Sales are ignored on purpose (it judges the buy). The benchmark series must be split-adjusted first. Feeds the chat tool `compare_buys_to_benchmark`.
- `metrics.ts` — quality metrics over a daily `{value, invested}` series (plain numbers — feeds directly from the cached timeseries JSON): `dailyReturns` (flow-adjusted `r_t = V_t/(V_{t−1}+ΔI_t) − 1`; deposits never masquerade as returns; **artifact guard: an extreme move (|r|>25%) on a flow-dominated day (|ΔI|>25% of prior value) is a valuation mismatch and is dropped** — one fake ±40% day from a mispriced import permanently poisons volatility/drawdown/peak tracking; real crashes on no-flow days survive), `chainReturns` (cumulative TWR), `annualize` (null under 2-day span, same guard as xirr), `volatility`/`sharpe` (**capital-weighted** via `DailyReturn.base` — each day weighs as much as the money it involved, so a $2k early-history era can't dominate the stats of the $200k it became; sharpe = annualized weighted-mean daily return − rf over weighted vol; population variance; drops exact-zero forward-fill days; ×√252; null <5 obs), `valueDrawdown` (**dollar-value** max/current drawdown — chart-consistent, deliberately flow-blind; the chained-index drawdowns told a user at ATH they were "58% below peak" because a tiny early LINK position once mooned), plus chained-index `maxDrawdown`/`currentDrawdown`/`bestWorstDay` (exported+tested, not shown in UI). All rates are floats. **The dashboard shows NO drawdown/peak metric at all** — max-DD, best/worst day, and off-your-peak were each rejected by the user; don't reintroduce one without asking. Compare's "Biggest drop" row uses **`materialDrawdown`** (2026-10-25): the flow-adjusted index's worst decline, counted only from the first day invested capital reached 10% of its peak, so selling never reads as a fall and a tiny early position can't define it. `valueDrawdown` (dollar series) told a real user "−90%": their first $1k was all LINK in 2021, and sales counted as losses (benchmarks read −35%; the real spring-2025 SPY drop was ~−19%, which is what it shows now). `seriesMetrics` returns `maxDrawdownFrom` (the start date); the dca cache key is `dca3`. **Companion rule in `computeTimeseries` (web): assets with zero price history are excluded from the replay entirely** — otherwise their cost counts in `invested` while value stays $0 forever (wedged chart + fake crash on the buy day; discovered on a real import: 71% vol / −90% max-DD / "36% off peak at ATH").
- `D()` normalizes `string|number|Decimal`; `toIsoDate()` for UTC date keys.
- **Target mix (`allocation.ts`, plain numbers like metrics.ts, 10 tests):** `allocationDrift(holdings, targets)` → one row per held-or-targeted key (current/target weight, drift = current − target, gapUsd = target × total − value; untargeted holdings have target 0), ordered by target then value. `fillToTarget(holdings, targets, amount)` splits a deposit by **water-filling**: the sleeve with the lowest value ÷ target weight is topped up first, joined by the next once level, so overweight and untargeted assets never get money, and a big enough deposit lands exactly on target. Cents via largest remainder, so the pieces always sum to the deposit. Client-safe subpath export `@beobeo/core/allocation` (no decimal.js in the browser bundle).
- **Next buy (`next-buy.ts`, R-004, plain numbers, 12 tests):** `pickNextBuy({amountUsd, portfolioValue, candidates, targets?, accounts?})` ranks 1–5 candidates for ONE buy of the whole amount: score = 0.6 × fit + 0.4 × dip (`NEXT_BUY_WEIGHTS`), or **0.9 × fit + 0.1 × dip with a target mix** (`NEXT_BUY_TARGET_WEIGHTS`): the shortfall decides and the dip only settles close calls (under 0.6/0.4 an overweight bond fund's dip outranked a sleeve twice as far short, mission 48). With targets, `compareShortfalls` rewrites the "short of target" reasons: the top says "the most of your options" and "all $X here takes it to Y%" when it overshoots, the others "less than <best>'s $Z" (or why a tie went the other way), and the dashboard adds a line pointing at Allocation's exact split when a pick overshoots. The "How this was picked" footer mirrors whichever weights apply; keep it in sync. Fit with a target mix = (target × (total + amount) − held) ÷ amount clamped to [0,1] (untargeted = 0); without one = 1 − weight after the buy. Dip = 0.7 × (1 − position in the trailing-year range) + 0.3 × (under-your-cost, full at −20%). Ties: lower weight after, then symbol. Each pick carries one plain `reason` sentence (the larger weighted part speaks; with ≥2 options the "N% of your portfolio" reason compares: the top pick "keeps your money more spread out than <runner-up> would", the others "spread your money less than <top>", since the bare weight read as a reason against), built in core so dashboard and chat say the same words, plus `placeAccount`: crypto → taxable, bond-like (`incomeHeavy`) → tax-advantaged (traditional, 401k, other, Roth), else the account that already holds it, else the first taxable; no reason with a single account.
- **Projection (`projection.ts`, plain numbers, 8 tests):** `projectGrowth({startValue, monthly, yearlyReturnPct, years, firstYearsPct?, yearlyRaisePct?, target?})` compounds monthly at (1+r)^(1/12) − 1 with the monthly amount added at each month's end (negative = withdrawal; raised once a year by `yearlyRaisePct`; `firstYearsPct` replaces the first years' returns for a bad-start stress). Returns the yearly path, end value, net put in, growth, and `targetInMonths` / `runsOutInMonths` (searched up to 100 years past the horizon; the last withdrawal only takes what's left). Feeds the chat tool `project_growth`.
- **Bracket picker (`tax-brackets.ts`, R-005, plain numbers, 4 tests):** 2026 federal thresholds on taxable income per `FilingStatus` (single / married_joint / head_of_household, IRS Rev. Proc. 2025-32; **re-check every November**). `bracketOptions(status)` = the sign-up bands (10% folded into 12%), each with its ordinary rate and the long-term rate at the band's lower edge; `ltcgRateAt(status, income)` = 0/15/20 on the next dollar; `ltcgZeroUpTo(status)` = the 0% bracket's top; `STANDARD_DEDUCTION` (2026, for the income hint); `taxableFromPay(status, pay)` (pay − standard deduction, floor 0) and `ratesAtIncome(status, taxable)` → `{band, ordinaryRatePct, ltcgRatePct}` (a band's lower bound belongs to it; the long-term rate follows the exact income, not the band's edge), used by welcome step 1's pay box and Tax Profile's rates check. Client-safe subpath export `@beobeo/core/tax-brackets`.
- **Tax Center engine** (`tax-netting.ts`/`tax-wash-sale.ts`/`tax-optimizer.ts`) — pure, no LLM involved (unlike the chat agent, this is deterministic tax math the UI narrates directly). `totalTax(shortTermNet, longTermNet, rates)` implements simplified federal netting (cross-net opposite-signed buckets → tax remaining gain at its own rate → up to $3,000 net loss against ordinary income → remainder as a carryforward discounted by `rates.carryforwardDiscount`) — **a lot is valued marginally as `totalTax(state+lot) − totalTax(state)`, never a flat rate table**, so the $3,000 boundary and cross-netting fall out of two function calls instead of special-casing. `detectWashSaleBlocks(lossLots, recentBuys, asOf)` only checks the trailing 30 days (the forward half of the 61-day window is unknowable for a planning tool — callers show a standing caution instead); a same-asset buy in ANY account (cross-account is the point) blocks the whole lot conservatively; a tax-advantaged trigger account is `permanentlyDisallowed` (Rev. Rul. 2008-5) vs. merely `deferred` for taxable — **the module never writes a basis adjustment anywhere, it only reports**, so "no mutation" is true by construction, not by discipline. `planSale({objective: "raise_cash"|"harvest_losses", ...})` — dynamic marginal-cost greedy fill, re-sorted after every addition, plus a bounded pairwise swap pass (`raise_cash` only); `planFifo`/`planHighestCostFirst` share the identical exact-tax-delta math with a static sort key, so the FIFO-vs-optimized headline number is apples-to-apples, never an approximation. `harvest_losses` is `raise_cash` with the candidate pool filtered to losses and no cash floor (take everything eligible) — literally the same engine, not a separate code path. `ripeningSoon`/inline `ripening` on a sale value a short-term lot (within 45 days of long-term) as ST-now vs. LT-later under the *same* baseline profile state, using the same totalTax-delta machinery. `explainNetting` is `totalTax`'s internals exposed as a breakdown (`{shortTermGainTaxed, longTermGainTaxed, ordinaryDeduction, carryforward, totalTax}`) instead of just the final number — `totalTax` is now a one-line wrapper around it, so there's exactly one implementation, never a UI-side reimplementation that could drift. `summarizeHarvest(profile, sales)` diffs `explainNetting` before vs. after a harvest to attribute the loss into three buckets (offsets existing gains / $3,000 ordinary deduction / carryforward) that always reconcile to the total harvested loss exactly, even across cross-netting — powers `loss-breakdown-bar.tsx`'s segmented bar, shown on **both** Harvest Losses and Raise Cash (whenever a plan sells losses, computed the same way in both `computeTaxHarvest`/`computeTaxPlan`) since a flat "+$X back" per lot didn't explain *why* each lot's number differed — same total loss lands at a different % depending on whether it's within the $3,000 cap or already spilling into the discounted carryforward. `taxOwedSoFar(profile)` = tax on the year's gains after carryforward + cross-netting, never negative (a bill, not a balance — a net loss's deduction value is not subtracted); powers the Now tab's verdict. **Crypto is exempt from the wash-sale rule (R-003):** `DEFAULT_WASH_SALE_EXEMPT_CLASSES = ["crypto"]` (§1091 covers stock/securities; the IRS treats crypto as property); `detectWashSaleBlocks(..., { exemptAssetClasses })` skips exempt `LossLotCandidate.assetClass` (a candidate with no class is always checked; pass `[]` if the law changes). `lossLocks(lots, profile, asOf, opts)` = "sell and buy straight back" moves: the harvest engine run on exempt-class lots only, grouped per asset, `taxSavedUsd` attributed in greedy order so the locks sum exactly to the joint total. Rebuying resets basis lower, so the UI must say the tax is deferred, not erased. **`taxMoves(lots, blocked, profile, asOf)` (R-003) = the one ranked "Moves available now" list**, values stacked in a fixed order so lock + harvest lines sum exactly to `lockAndHarvestSavedUsd`: `lock` (crypto sell-and-buy-back, from `lossLocks`) → `harvest` (other unblocked losses per asset, valued on top of the locks, `rebuyAfter` = asOf + 31 days) → `on_hold` (wash-sale-blocked losses per asset, `clearsOn` = latest trigger + 31 days, valued on top of 1+2 as if sold that day; `valueUsd: null` when that's next year; `permanentlyDisallowed` for IRA rebuys) → `wait` (gain lots turning long-term within 45 days, per asset, each lot valued alone like `ripeningSoon`). Also returns `breakdown` (`summarizeHarvest` of every lock+harvest sale), `deductionRoomUsd` (the $3,000 not yet used by this year's net loss) and `deadline` (Dec 31). **0% long-term room (R-003, 2026-10-28):** with `opts.income` (`IncomeInfo` = filing status + taxable income before gains) it appends `zero_gain` moves from `zeroRateGains`: room = `ltcgZeroUpTo(status)` − income − max(0, the year's net gain as it stands, not after the loss moves); none when the year nets to a loss; fill long-term gain lots by gain ÷ proceeds, whole shares (crypto 8 dp), skipping assets with a loss move or hold (a rebuy would restart their wash-sale wait); valued at 15% on a later sale, not counted in `lockAndHarvestSavedUsd`. `zeroRateRoomUsd` is null without income. `profileAtIncome(profile, income, federalLtcgRate)` drops the federal long-term rate when income + net gain fits in 0% (a straddling year keeps the full rate); callers apply it before `taxMoves`/`taxOwedSoFar`. **`sellEverything(lots, blocked, profile, asOf, {income, federalLtcgRate})`** (2026-10-28) = "roughly what would I owe if I sold it all": every lot's gain by term added to the year's position, priced as `taxOwedSoFar(after) − taxOwedSoFar(now)` (negative when the sale's losses cut tax already owed), each side income-adjusted via `profileAtIncome` (so a sale that pushes the year out of 0% pays full rate); losses a retirement-account rebuy disallows for good are left out (`disallowedLossUsd`), a taxable-account rebuy would be sold too so its loss counts; pass the saved profile, not an income-adjusted one. 55 golden-case tests in `test/tax-{netting,wash-sale,optimizer}.test.ts`.

### `packages/db`
- Auth tables prefixed `auth_*` (Better Auth managed: `auth_user`, `auth_session`, `auth_account`, `auth_verification`) so domain `accounts` keeps the natural name.
- Domain: `portfolios` (named containers, e.g. "Main"/"Retirement"; a user's accounts each carry a `portfolioId` FK — nullable only for legacy rows, the app always sets it), `accounts` (user's brokerages; `accountType` enum taxable/traditional_ira/roth_ira/401k/other_tax_advantaged, defaults taxable), `assets` (shared across users; unique on symbol+class; `providerRef` = CoinGecko id), `transactions` (enum type: buy/sell/dividend/split/transfer_in/transfer_out/fee; `numeric(38,18)` quantities, `numeric(38,10)` money; `source` tracks provenance: manual/csv:\<preset\>/seed), `price_history` (shared cache; unique assetId+date), `asset_splits` (shared corporate actions from providers; unique assetId+date; ratio = 4 for 4-for-1), `chat_threads`/`chat_messages` (content jsonb `{text}` — text-only persistence, tool blocks not replayed), `tax_profiles` (Tax Center settings, see apps/web section for why it's keyed per-portfolio, not per-user).
- **Every DB request has a deadline (`src/fetch-timeout.ts`, installed in `client.ts` via the global `neonConfig.fetchFunction`).** The Neon HTTP driver has none, and a stalled request once held a page 8.6 minutes (Tax Center p95 ~16 min) while the same query answered in ~1s right after. A single SELECT gets 15s and is retried once. Writes and batches (`{queries:[…]}`) get 60s and are never retried, because a timed-out write may have committed. Each timeout logs `[db] read|write timed out…` in the dev log. A stall while the driver reads the response body still errors at the deadline, but isn't retried. If a legitimate query ever needs more than 15s, batch or narrow it rather than raising the deadline. Tests: `packages/db/test/fetch-timeout.test.ts`.
- Schema workflow is `db:push` (no committed migrations yet). If/when going to production with real users, switch to generated migrations.

### `packages/market-data`
- `MarketDataService(db, config)` — **cache-first**: reads `price_history`, computes uncovered spans via pure `planFetch(coverage, from, to, staleDays=4)` (staleDays tolerates weekends), fetches only gaps, upserts with `onConflictDoNothing`.
- **Bulk reads are the primary API (perf-critical on Neon):** the Neon serverless HTTP driver *serializes* concurrent queries (~70ms each even under `Promise.all`), so per-asset loops cost seconds. `getPricesBulk(assets, from, to)` and `getLatestPrices(assets, to)` do one grouped coverage query + one rows query (+ one `DISTINCT ON` for latest) for ALL assets; the singular `getPrices`/`getLatestPrice` are thin delegates. **Never add a per-asset query loop over this driver — batch it into one SQL statement.** A 30s in-process coverage memo lets the overview/timeseries/compare request burst share one coverage query (entries dropped after provider upserts).
- **Per-asset windows + negative caching (don't regress):** `DbAsset.seriesFrom` narrows an asset's ensure-window to its own first transaction — without it, any asset that IPO'd after the portfolio-wide window start is a *permanent head gap* (provider has no pre-listing data) re-fetched on every load. Ranges a provider confirms empty are negative-cached in-process for 12h; failed fetches back off 5min — otherwise every read stalls behind provider throttles retrying unfillable gaps.
- **Every provider request carries `signal: providerSignal()` (20s deadline, `rate-limit.ts`, body included).** Throttles serialize calls, so one request that never answered used to hold the queue and stall every price read behind it (a dashboard load took 10.7 min even after DB timeouts landed). A timeout is an ordinary provider failure (next provider, then the 5-min backoff). Any new provider call must pass it.
- Provider chains: equities Tiingo → AlphaVantage; crypto **Coinbase Exchange (keyless, primary)** → CoinGecko. Fallback on any error except `NOT_FOUND` (which propagates). Providers take `fetchImpl` for test mocking; each has a `Throttle` (serialized min-interval).
- **Unadjusted closes on purpose** — splits are modeled as transactions; adjusted closes would double-count.
- **Splits (`asset_splits` table, shared like price_history):** Tiingo's `splitFactor` column is captured on every fetch and upserted (`ratio` convention: 4 = 4-for-1; the close ON the split date is already post-split). `getSplits(assetIds)` bulk-reads them; `syncCorporateActions(asset, from, to)` re-fetches a full range to catch splits inside already-covered spans (the gap-based cache never revisits them) — the backfill script runs it for every cached non-crypto asset. New assets need nothing (first full fetch captures splits). AlphaVantage/Coinbase provide no split data.
- Coinbase Exchange: `products/<SYMBOL>-USD/candles`, granularity 86400, paginated in 300-candle windows, candles arrive newest-first.
- AlphaVantage signals rate limits via HTTP 200 + `Note`/`Information` body fields.
- Search: static `POPULAR_ASSETS` fast path first (`popular.ts` — famous tickers answer instantly, zero network; ≥5 popular hits skip providers entirely), then Tiingo (equities) + CoinGecko (crypto, needs key) merged best-effort. **All search results dedupe on symbol+class** — Tiingo lists share classes separately (META twice), which once crashed React keys in the picker. Tiingo search/quotes use a separate 250ms `interactiveThrottle` so user-facing lookups never queue behind 1.2s-throttled historical backfills.
- `getPriceForDate(asset, date)` — intraday quote when date is today (Tiingo IEX `/iex/?tickers=`, Coinbase Exchange `/products/X-USD/ticker`; providers expose optional `getIntradayQuote`), else last close ≤ date. Powers the transaction form's price auto-fill (`assets.priceOn` tRPC proc).
- **Resilient reads:** `getPrices`/`getLatestPrice` swallow `ensureCached` failures and serve whatever is cached — a rate-limited provider (Tiingo hourly cap gets exhausted by big-import backfill storms) must never blank prices the DB already has. `ensureCached` also dedupes concurrent identical fetches via an in-flight map (overview + timeseries fire together).
- **Live prices for today (2026-10-29, user-reported: BTC showed $80k, the Oct 27 close, while it traded at $77k):** `getLatestPrices(assets, to)` overlays a live quote (dated today) whenever `to` is today, so the dashboard, chat snapshot, next buy and export all value holdings live. `getLiveQuotes` memoizes quotes 60s (failures 5 min), waits at most 2.5s before serving cached closes (late quotes still fill the memo), sends all equities in one Tiingo IEX request (`getIntradayQuotes`, comma-separated tickers) and asks Coinbase per crypto asset. The cache counts crypto stale after 1 missing day (equities 4, for weekends), and today's crypto candle is never stored, since it keeps moving until UTC midnight and `onConflictDoNothing` would freeze it as the close. Charts still end at the last daily close.
- **`getLatestPrice` fetches a 10-day trailing window, never a single day** — a lone-day fetch on a weekend/holiday (or on a fresh asset with no coverage) caches nothing and the lookup returns null. Don't regress this.
- **All series loads use a 14-day price lead-in** (`leadIn()` in `apps/web/src/server/portfolio.ts`, applied in `loadPriceSeriesForAssets`, `computePosition`, `computeDcaComparison`) and `portfolioTimeSeries` **seeds forward-fill from the newest close before the window** — otherwise a position bought today (no close yet) charts at $0. Same-day-buy portfolios were the original bug report.
- `xirr` returns null for spans under ~2 days (annualizing a same-day gain is numerical noise); the compare page renders null as "—" and shows "Dead even so far" for zero deltas.
- The package has **client-safe subpath exports**: `@beobeo/market-data/popular` (static list + `searchPopular`, no DB imports) is imported by browser components; the root export pulls in drizzle/db and is server-only.
- Web app uses a process-wide singleton: `getMarketData()` in `apps/web/src/server/market-data.ts` (throttles must be shared).

### `packages/importers`

A Claude session, usage or weekly limit is a pause, not a stop (the weekly one was once read as two stalls and ended the cycle): the round is retried after the reset time parsed from the message ("resets 1:20pm"), the wait doesn't count against the budget, and a Mac notification says when it resumes (gives up if the reset is more than `EVOLVE_MAX_WAIT_HOURS`, default 6, away). The script then runs `typecheck/lint/test/build` itself, writes the report's `Checks:` line (rounds leave it `PENDING`) and, if passed, merges `evolve/<date>` into the base the same day. Rounds that can't get green `git stash push` their work instead of committing it. `--evolve-only` reuses today's digest to build more without re-simulating. Safety valve: ≥3 branches that couldn't be merged or two consecutive `Checks: FAILED` reports → propose-only. When the cycle ends (or dies after taking the lock) it posts a macOS notification (`osascript`) with the report's `Checks:` line. Commands: `.claude/commands/evolve.md`, `evolve-agents.md` (Sundays).

**Chat state rule (bug fixed 2026-07-13, don't reintroduce):** the streamed conversation in local state is the single source of truth while the page is open. Saved messages load **once, imperatively** via `queryClient.fetchQuery` (30s staleTime; prefetched on hover; every `chat.messages` entry is invalidated after a send) in an effect that runs only when the open `threadId` differs from `loadedId`, the thread whose messages are on screen. A new thread's `thread` SSE event sets both, so it never reloads mid-stream. Never add a reactive `useQuery`+`useEffect` that overwrites `messages` from the cache — the stale-cache overwrite on `streaming` flips made bubbles duplicate/disappear mid-conversation. **The open thread is remembered per user on the device** (`useStoredState("beobeo.chat.thread.<userId>")`), so leaving Chat and coming back reopens it; "New chat" clears it, and a stored thread that loads empty or fails is forgotten (the chat route 404s unknown ids). While a thread loads, the page shows "Opening your conversation…", never the empty "What would you like to know?" state: that flash read as "my chat is gone" (augusta, mission 11).
